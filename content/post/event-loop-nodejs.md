«Микротаски выполняются раньше макротасков» — этого достаточно для мидла. На senior-интервью
чаще спрашивают то, что ломает эту упрощённую модель: что происходит, когда микрозадача сама
порождает новую задачу, и почему в Node.js `process.nextTick` — это не то же самое, что
`queueMicrotask`.

## Базовая модель: одна очередь недостаточна

Стек вызовов (call stack) выполняет синхронный код. Когда он пустеет, event loop решает, что
запустить дальше. В браузере всё просто: одна очередь микрозадач (промисы и `queueMicrotask`),
которая полностью опустошается перед следующим макротаском (`setTimeout`, событие, рендер).

В Node.js очередей две, и у них разный приоритет:

- **`process.nextTick`** — своя отдельная очередь, специфичная для Node.js. Аналога в браузере нет.
- **Микрозадачи** — промисы (`.then`) и `queueMicrotask`, как в браузере.

Ключевое правило, которое обычно и проверяют: **очередь `nextTick` имеет приоритет над очередью
микрозадач и опустошается полностью между *каждой* микрозадачей**, а не один раз в конце.

## Пример, который стоит уметь трассировать вслух

```js
console.log('A');

setTimeout(() => console.log('B'), 0);

process.nextTick(() => {
  console.log('C');
});

Promise.resolve()
  .then(() => {
    console.log('D');
    process.nextTick(() => {
      console.log('E');
    });
  })
  .then(() => {
    console.log('F');
  });

queueMicrotask(() => {
  console.log('G');
});

async function fn() {
  console.log('H');
  await null;
  console.log('I');
}
fn();

console.log('J');
```

Результат: `A H J C D E G I F B`.

### Почему именно так

1. **Синхронный проход.** Стек выполняет код сверху вниз без остановок: `A`, затем внутри `fn()`
   код до первого `await` выполняется синхронно — `H`, затем `J`. `await null` не «ждёт» ничего
   в смысле реального времени: он оборачивает значение в `Promise.resolve(null)` и откладывает
   продолжение (`I`) в очередь микрозадач — это работает одинаково для *любого* значения после
   `await`, даже не-промиса. Это частая ловушка: кажется, что раз значение не промис, продолжение
   выполнится синхронно — нет, не выполнится.

   К моменту, когда стек опустел, очереди выглядят так:
   - `nextTick`: `[C]`
   - микрозадачи: `[D, G, I]` (именно в этом порядке — `D` зарегистрирован раньше `G`, а `I`
     позже обоих, потому что `fn()` вызван после `queueMicrotask(G)`)

2. **`nextTick` опустошается первым.** `C` выполняется раньше любой микрозадачи — печатает `C`.

3. **Дальше идёт очередь микрозадач, но с проверкой `nextTick` после каждого шага.** Выполняется
   `D` → печатает `D`. Внутри `D` регистрируется `process.nextTick(E)`. Здесь и есть главный
   момент: Node не ждёт, пока опустеет вся очередь микрозадач — он **сразу же проверяет очередь
   `nextTick`** и находит там `E`. `E` выполняется немедленно, раньше `G` и `I`, хотя они были
   поставлены в очередь раньше. Плюс завершение `D` резолвит промис, к которому привязан `.then(F)`
   — `F` встаёт в конец очереди микрозадач.

4. Очередь микрозадач продолжает опустошаться: `G`, затем `I`, затем `F`. После каждого шага
   Node снова проверяет `nextTick` — но она уже пуста.

5. Только когда обе очереди полностью пусты, event loop переходит к следующей фазе —
   **timers** — и выполняет колбэк `setTimeout`: `B`.

Итог: `A H J C D E G I F B`.

## Фазы event loop — не только timers

Синхронный код и очереди `nextTick`/микрозадач — это то, что спрашивают чаще всего, но полная
картина Node.js — это цикл из фаз, и после *каждого* колбэка в любой фазе снова опустошаются
`nextTick` и микрозадачи:

- **timers** — колбэки `setTimeout`/`setInterval`, время которых истекло
- **pending callbacks** — отложенные системные колбэки (например, некоторые ошибки TCP)
- **poll** — получение новых I/O-событий, выполнение их колбэков; здесь event loop может
  заблокироваться в ожидании, если нет других задач
- **check** — колбэки `setImmediate`
- **close callbacks** — колбэки закрытия (`socket.on('close', ...)`)

Частый вопрос на этом уровне: **`setTimeout(fn, 0)` vs `setImmediate(fn)`** внутри I/O-колбэка.
Внутри цикла `fs.readFile` (то есть уже в фазе poll) `setImmediate` гарантированно выполнится
раньше `setTimeout(fn, 0)`, потому что следующая фаза после poll — это check, а до timers дойдёт
только на следующем витке цикла. Вне I/O-колбэка порядок между ними не гарантирован — зависит от
того, сколько реально заняло время до входа в event loop.

## Практическое следствие, не только теория

Рекурсивный `process.nextTick` (например, планирование следующего тика прямо из текущего)
может **заблокировать переход к I/O бесконечно** — цикл никогда не дойдёт до фазы poll, потому
что очередь `nextTick` обязана опустеть полностью перед любой следующей фазой. Это реальная
причина, по которой в Node.js `nextTick` стоит использовать для действительно приоритетных вещей
(например, гарантированный вызов колбэка асинхронно, а не синхронно — паттерн «release Zalgo»),
а не как замену `setImmediate` для «отложить на потом».

## Коротко

- В браузере — одна очередь микрозадач. В Node.js — две, и `nextTick` приоритетнее.
- `nextTick` опустошается между *каждой* микрозадачей, а не один раз за цикл.
- `await` откладывает продолжение в микрозадачу для любого значения, не только для промиса.
- Полная картина — это фазы (timers → pending → poll → check → close), между которыми снова
  опустошаются `nextTick` и микрозадачи.
