Если до этого писал на голом Express, первая реакция на NestJS — «зачем так много файлов ради
одной ручки GET `/`». Ответ не в бюрократии, а в том, что NestJS явно разделяет три роли, которые
в Express обычно свалены в один файл: точку входа, слой роутинга и слой бизнес-логики — и
связывает их через DI-контейнер, а не через ручные `require`/импорты.

## Четыре файла минимального приложения

```
src/
├── main.ts
├── app.module.ts
├── app.controller.ts
└── app.service.ts
```

### `main.ts` — точка входа

```ts
import {NestFactory} from '@nestjs/core';
import {AppModule} from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(3000);
}
bootstrap();
```

`NestFactory.create(AppModule)` — не просто аналог `express()`. На этом шаге Nest строит граф
зависимостей всего приложения: читает метадату модуля, инстанцирует все провайдеры в правильном
порядке и подключает контроллеры к внутреннему HTTP-адаптеру (по умолчанию — Express, можно
заменить на Fastify).

### `app.module.ts` — единица сборки

```ts
import {Module} from '@nestjs/common';
import {AppController} from './app.controller';
import {AppService} from './app.service';

@Module({
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}
```

Модуль — это не папка и не namespace, а декларация: «вот контроллеры этого модуля, вот провайдеры,
которые им доступны для инъекции». Забыл добавить сервис в `providers` — при старте получишь
runtime-ошибку вида `Nest can't resolve dependencies of AppController` с указанием, какого именно
провайдера не хватает. Это самая частая ошибка новичка в NestJS, и сообщение об ошибке обычно
прямо называет причину.

### `app.controller.ts` — тонкий слой роутинга

```ts
import {Controller, Get} from '@nestjs/common';
import {AppService} from './app.service';

@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}

  @Get()
  getHello(): string {
    return this.appService.getHello();
  }
}
```

Контроллер получает сервис не через `import` и `new`, а через конструктор — это и есть
dependency injection. Nest видит тип параметра (`AppService`) в конструкторе, находит
соответствующий провайдер в графе модуля и подставляет готовый экземпляр сам.

### `app.service.ts` — бизнес-логика

```ts
import {Injectable} from '@nestjs/common';

@Injectable()
export class AppService {
  getHello(): string {
    return 'Hello World!';
  }
}
```

`@Injectable()` — это не просто пометка «это сервис». Декоратор регистрирует метадату класса,
которую NestJS читает через `reflect-metadata`, чтобы знать, как и с чем этот класс можно
инстанцировать и внедрять в другие классы.

## Почему это вообще так устроено

За декораторами (`@Module`, `@Controller`, `@Injectable`, `@Get`) стоит DI-контейнер: он решает,
в каком порядке создавать классы, и подставляет зависимости через конструктор, а не через ручной
импорт синглтона. Практическое следствие — тестируемость: в юнит-тесте контроллера не нужен
реальный HTTP-сервер и реальная база, сервис подменяется мок-объектом через тот же механизм
инъекции, без правки кода контроллера.

Цена этого подхода — та самая «лишняя» структура на маленьком проекте: чтобы добавить одну ручку,
трогаешь минимум два файла (контроллер + модуль), иногда три (плюс сервис). На небольшом REST API
это ощущается как оверинжиниринг. Компромисс раскрывается на масштабе: когда ручек не одна, а
сотни, и логика реально переиспользуется между контроллерами — жёсткое разделение
роутинг/логика/сборка перестаёт быть накладными расходами и становится единственным способом не
утонуть в графе зависимостей вручную.

## Коротко

- `main.ts` запускает `NestFactory.create()`, который строит весь граф зависимостей приложения.
- Модуль — декларация связей между контроллерами и провайдерами, а не просто группировка файлов.
- Контроллер получает зависимости через конструктор — DI-контейнер сам находит подходящий
  провайдер по типу параметра.
- Самая частая ошибка новичка — забыть добавить провайдер в `providers` модуля; сообщение об
  ошибке при старте обычно прямо называет недостающий класс.
