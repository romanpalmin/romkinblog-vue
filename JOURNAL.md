## 2026-08-14 — Phase 5: первый реальный деплой на romkin.blog

- Параллельно с этим — закрыли Вариант 3 ДЗ №11 курса по вайб-кодингу
  («задеплой свой проект»), см.
  `../../job-search/WorkHunter/courses/vibe-coding-claude-code/homework/hw-11-deploy.md`
  для полного разбора. Здесь — только специфичное для проекта.
- **Находка перед началом работы:** `www/README.md` в `WorkHunter` утверждал
  «хостинг и git пока не настроены» — оказалось устарело. `romkin.blog`
  уже был живой (DNS, HTTPS, домен куплены раньше, заглушка отдавалась с
  реального хостинга). FTP-порт был открыт, доступы нашлись в панели
  хостинга — экономия целой фазы «купить хостинг».
- Хостинг — `nichost.ru`, путь на сервере `/romkin.blog/docs/`. Этот путь
  совпал 1:1 с тем, что уже было прописано в
  `../romkinblogsimple/.github/workflows/main.yml` — значит текущий и
  прошлый проект физически делят один и тот же хостинг-аккаунт.
- **Проверка перед деплоем: SSG действительно статический.** Несмотря на
  `routeRules: { '/': { ssr: true } } ` в `nuxt.config.ts`, было
  сомнение, не потребуется ли `ssr: false`. Проверили руками:
  `nvm use 24 && npx nuxi generate`, затем подняли результат через
  `npx serve .output/public` — все маршруты отдают готовый, полностью
  отрендеренный HTML (не пустой SPA-shell под гидратацию). `ssr: true` в
  routeRules — это про то, как краулер рендерит маршрут во время сборки,
  не про рантайм-зависимость от сервера. Трогать не пришлось.
- Workflow адаптирован из `romkinblogsimple`, но не скопирован дословно:
  Node 20 → 24 (CLI Nuxt использует `node:util.styleText`, которого нет в
  Node 20.10 — та же причина, что и в `CLAUDE.md` для локальной разработки),
  убраны хаки вокруг `better-sqlite3` (там это была проблема разрешения
  версий, здесь — обычная зависимость в `package.json`).
- Осознанно исключили `**/backup/**` в FTP-деплое — на сервере в
  `docs/backup/` лежит что-то от старой версии сайта, не должно
  пострадать от синхронизации. Проверили заранее (не наугад): по
  документации `SamKirkland/FTP-Deploy-Action` дефолтное поведение и так
  не трогает файлы, не отслеживаемые state-файлом действия (первый деплой
  ничего не удаляет, `dangerous-clean-slate` по умолчанию `false`) — но
  явный exclude оставили как дополнительную страховку.
- **Грабли #1:** `git push` с новым `.github/workflows/main.yml` упал —
  `refusing to allow an OAuth App to create or update workflow ... without
  'workflow' scope`. У локального `gh` CLI токена не было scope
  `workflow`. Чинится `gh auth refresh -s workflow` — но это device flow,
  нужно подтверждение в браузере, не бесшовно.
- **Грабли #2:** первый реальный прогон Actions упал на самом FTP-шаге —
  `530 Login incorrect`. Секреты `FTP_PASSWORD`/`FTP_USERNAME`, вписанные
  с первого раза, не подошли (опечатка при копипасте или не тот пароль).
  Перевписали — второй прогон прошёл зелёным целиком.
- **Итог проверен не на глаз, а по факту:** `content-length` живой
  `https://romkin.blog/` (69291 байт) сверен с размером локально
  собранного `.output/public/index.html` — совпал байт в байт, значит на
  сервере действительно та сборка, которую тестировали, а не что-то
  промежуточное.
- **Не наша поломка, но заметили:** редирект `/cv` → `/cv/`, который
  генерирует сам хостинг (не Nuxt/не этот workflow), уходит на `http://`,
  не `https://`. Не блокирует (страница всё равно открывается), но если
  когда-то будет странно ругаться на mixed content — вот источник.
