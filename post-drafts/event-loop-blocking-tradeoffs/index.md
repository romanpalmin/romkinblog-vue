Разберём вопрос, который на собеседовании обычно звучит как «что будет, если внутри обработчика
запроса выполнить тяжёлые синхронные вычисления», а в проде звучит куда менее академично —
как жалоба «сервис иногда встаёт колом на 2–3 секунды без видимой причины». Причина, как правило,
одна и та же: JS-код в Node.js выполняется в один поток, и любая синхронная CPU-тяжёлая операция
(рекурсивные вычисления, `JSON.stringify` на большом объекте, хеширование без колбэка, регулярка
с катастрофическим бэктрекингом) блокирует не только текущий обработчик — она блокирует вообще
всё: остальные запросы, I/O-колбэки, таймеры, — пока не завершится сама.

Это не баг event loop, а прямое следствие модели: параллелизм в Node.js честный только на уровне
I/O (через libuv и его пул потоков под капотом), а не на уровне выполнения JS-кода. Вопрос не
«избежать ли это», а какой из вариантов архитектурного решения соразмерен вашей конкретной
нагрузке — благо вариантов несколько, и у каждого свой набор компромиссов.

## Вариант 1 — `worker_threads`

Реальные OS-треды, каждый со своим V8-инстансом и своим event loop, обмен данными — через
`postMessage` (с сериализацией) или `SharedArrayBuffer` (без копирования, но с ручной
синхронизацией доступа).

**Преимущества:**
* настоящий параллелизм для CPU-bound задачи — главный поток остаётся отзывчивым;
* можно передавать большие бинарные данные почти без накладных расходов через `SharedArrayBuffer`.

**Сложности:**
* сериализация через `postMessage` для сложных объектов сама по себе не бесплатна — на очень
  больших payload может съесть часть выигрыша;
* добавляет message-passing архитектуру там, где раньше был прямой вызов функции — усложняет
  отладку и обработку ошибок;
* оверхед на создание воркера ощутим для мелких, но частых задач — есть смысл держать пул
  воркеров, а не создавать новый на каждый запрос.

## Вариант 2 — `cluster` / несколько процессов

Форк нескольких Node-процессов (обычно по числу ядер), общий слушающий сокет, балансировка между
процессами — на большинстве платформ round-robin.

**Преимущества:**
* один заблокированный процесс не останавливает остальные — сервис в целом остаётся отзывчивым
  для параллельных запросов;
* не требует переписывать код под message-passing — каждый процесс работает как обычное
  однопоточное Node-приложение.

**Сложности:**
* внутри одного процесса блокировка событийного цикла никуда не делась — если конкретный запрос
  попал именно в заблокированный процесс, ему всё равно придётся ждать;
* процессы не разделяют память — состояние в оперативке (кэш, сессии) нужно выносить во внешнее
  хранилище (Redis и подобное), иначе оно расползётся по процессам независимо;
* не параллелизует одно тяжёлое вычисление — параллелизуются только независимые запросы.

## Вариант 3 — вынос в отдельный сервис/очередь

CPU-тяжёлая работа уезжает в выделенный воркер-сервис (очередь вроде BullMQ/RabbitMQ, отдельный
процесс или вообще сервис на другом языке, если он объективно быстрее для конкретной задачи),
а API-слой остаётся тонким и исключительно I/O-bound.

**Преимущества:**
* архитектурно самый чистый вариант на масштабе — API не деградирует от вычислительной нагрузки
  вообще, воркеры масштабируются отдельно и независимо от API;
* воркер можно писать не на Node.js, если для конкретной задачи есть более подходящий инструмент
  (это тоже стоит держать в голове как опцию, а не считать Node.js единственным вариантом по
  умолчанию).

**Сложности:**
* добавляет реальную инфраструктуру — очередь, отдельный деплой воркеров, мониторинг ещё одного
  движущегося компонента системы;
* для небольшого проекта это, скорее всего, избыточно — оверинжиниринг ради проблемы, которой
  пока нет (если, конечно, у вас не тысячи запросов в секунду уже сегодня, тогда это, наоборот,
  единственный разумный вариант).

## Вариант 4 — чанкинг синхронной работы

Тяжёлое вычисление разбивается на куски, между которыми выполнение явно отдаётся обратно event
loop (`setImmediate`, реже `setTimeout`), либо вместо загрузки всего в память разом используется
потоковая обработка (streams).

**Преимущества:**
* не требует новой инфраструктуры и новых процессов — самый дешёвый вариант по трудозатратам;
* снимает полную блокировку event loop, оставляя его отзывчивым между чанками.

**Сложности:**
* не добавляет параллелизма — суммарное время вычисления не сокращается, просто перестаёт быть
  одним долгим блоком; для действительно тяжёлой задачи это паллиатив, а не решение;
* усложняет код самой функции — линейный синхронный алгоритм превращается в набор шагов с явной
  передачей управления.

## Что я не берусь оценить абстрактно

Если CPU-нагрузка идёт не от вашего кода, а от конкретной нативной зависимости с биндингами
(например, тяжёлая криптография или обработка изображений через нативный модуль) — дать честную
оценку без знания конкретной библиотеки я не готов: там решение часто завязано на то, отдаёт ли
сама библиотека асинхронный API или заставляет блокировать поток независимо от того, что вы
делаете сверху.

## Вместо готового ответа — вопросы, которые стоит задать себе

Универсального «правильного» варианта из четырёх выше нет — правильный зависит от характера
нагрузки, которого я, естественно, не знаю про ваш конкретный проект. Стоит честно ответить себе:

* Тяжёлая операция — редкое исключение или постоянная часть трафика?
* Насколько критична задержка именно во время самой тяжёлой операции — можно ли ей работать
  с более низким приоритетом, чем остальному трафику?
* Нужно ли делить память/состояние между вычислением и остальным приложением, или данные можно
  спокойно сериализовать при передаче?
* Уже есть в стеке очередь или похожая инфраструктура — или её пришлось бы поднимать с нуля
  ради этой одной задачи?
* Какой сейчас реальный масштаб — тот, на котором `cluster` уже даёт эффект, или трафика пока
  объективно мало и любое из решений будет преждевременной оптимизацией?

Если после честных ответов на эти вопросы всё ещё не очевидно, какой вариант ваш — это нормально,
на практике часто нужен один быстрый эксперимент (профилирование конкретной тяжёлой функции под
реальной нагрузкой), а не попытка выбрать архитектуру заранее по одной статье в интернете :)
